## 2026-08-20 — T-047 [pipeline-agent]
Decided: `feature_spec.json` v2 replaces the three fixed transformation categories
(`encodings`/`null_handling`/`interactions`) with a single open-vocabulary `features` list. Each
entry is `columns` (1..N non-empty strings) / `operation` (free-form string) / `params` /
`fit_scope` (required, no default) / `rationale`, rebuilt from that whitelist so the LLM's own

put them, and either dropped them or smuggled them into `encodings` with an invented `method`.

returning it, which T-016's `analysis_critic._detect_phase_stem` discriminator depends on.

## 2026-08-20 — T-047 [pipeline-agent]
Decided: the fit-scope guard covers six leakage-prone families — target encoding, statistical
imputation, scaling/normalization, binning/discretization, dimensionality reduction, and
frequency/count encoding. A match *requires* `fit_scope: "per_fold"`; no match means no check. The
matching mechanism is T-022's, verbatim: whole-phrase `\b...\b` regex against a separator-normalized
(`-`/`_` → space) lowercase copy, with the curated target-encoding tuple carried over unchanged.
Why: conservative asymmetry. Forcing `per_fold` on an operation that turns out to be stateless
produces identical output; missing a fitted one is a silent leak that inflates every CV score for
the rest of the run. Severity is explicitly two-tier and documented as such — target encoding leaks
the *target* and breaks CV outright, the other five leak only held-out-fold *feature* statistics —
so the uniform rejection is a stated stance, not a claim the two are the same bug. No bare stem
(`scale`, `transform`, `encoding`, `impute`, `mean`, `count`, `normalize`) is ever a keyword,
because each appears inside legitimately stateless names.
Affects: `src/nodes/llm/feature_engineer.py`, `config/prompts/feature_engineer/v2.md`.
Discarded: an allow-list of stateless operations (unbounded, and it would reject the novel
operations v2 exists to permit); inferring scope from `params` (nothing in `params` distinguishes a
fitted operation); emitting a warning instead of rejecting (nothing in the pipeline consumes
warnings — a critic-retry `ValueError` is the only feedback channel that reaches the LLM).
Note: `frequency_encoding_excluding_target_leak` — T-022's canonical false positive — is now
legitimately flagged, by the *frequency/count encoding* family. The property T-022 protected still
holds: it is not flagged as **target** encoding. It simply belongs to a family T-022 did not have,
and frequency encoding does learn global category counts.

## 2026-08-20 — T-047 [pipeline-agent]
Decided: the T-047 review fix round changes the keyword floor itself, which the pre-review ruling
had frozen. Four tuple corrections and one mechanism change. `_TARGET_ENCODING_KEYWORDS` is
therefore **no longer carried byte-for-byte from T-022** — `target encode` and `target encoder` are
added to it; the earlier entry above, which says the tuple survives unchanged, is superseded on
that point only. `_SCALER_KEYWORDS` loses `unit norm` and `l2 normalize` and gains `standardize`,
`standardization`, `zscore`, `maxabs` and `max abs scaling`. `_STATISTICAL_IMPUTATION_KEYWORDS`
gains the verb-first and pandas phrasings (`impute_median`, `fillna_median`, `median_fill` and
their mean/mode counterparts, `simple_impute`). And `_normalize_operation` now splits camelCase
before lowercasing, extending the matching mechanism T-022's adversarial review established rather
than replacing it. Two structural validation rules land in the same round: duplicate column names
inside one entry, and two entries sharing a `(columns, operation)` pair, are both rejected;
`operation` and `rationale` are written stripped.
Why: executed evidence, not judgement. The review ran `_matched_fit_scope_family` against real
strings. `l2_normalize` was **flagged** although sklearn's `Normalizer` is stateless and row-wise —
so a *correct* `global` declaration raised, and `LLMNode.__call__` has no `try/except`, meaning a
conforming response terminated the Phase 4 run. `standardize`, `maxabs_scale`, `zscore_*`,
`fillna_median`, `impute_median`, `simple_impute`, `target_encode`, `target_encoder` and
`TargetEncoder` all returned `None` and were written with `fit_scope: "global"`. The
target-encoding gap is the severe one — that family is target leakage, not feature-statistic
leakage — and it exists on `main` too, inherited from T-022; it is fixed here because this PR
promotes the tuple to the sole floor for that family and because this PR's own
`_FREQUENCY_ENCODING_KEYWORDS` already lists both the noun and the verb form, making the asymmetry
indefensible once seen. camelCase matters because `TargetEncoder`, `StandardScaler`,
`MinMaxScaler`, `KNNImputer` and `SimpleImputer` are sklearn's actual class names, are highly
probable `operation` values, and were reachable by **no** keyword in any tuple.
Affects: `src/nodes/llm/feature_engineer.py`, `tests/unit/nodes/llm/test_feature_engineer.py`,
`config/prompts/feature_engineer/v2.md`, `docs/pipeline.md` § the `feature_spec.json` contract.
Implementation note: `_matched_fit_scope_family` matches against **both** the camel-split and the
unsplit normalization. Splitting alone would have broken a pre-existing match — `CatBoost encoding`
splits to `cat boost encoding`, which no longer matches the concatenated `catboost` keyword — so
the split is added on top of the old reading rather than traded for it. The split form can only
differ for an input containing an internal capital, so it introduces no false positive the unsplit
form did not already have; the "merely mentions a family word" and "unrecognized operation is
accepted" suites both stay green. Not covered, and stated rather than assumed: an unseparated
all-lowercase run (`targetencoder`) matches nothing.
Discarded: a `schema_version` key on the artifact — **human ruling**: it would add a key to the
contract `docs/pipeline.md` has just pinned and that T-029 will inherit, no live path breaks
without it (`analysis_critic` reads the file as raw text; `resolve_feature_spec_ref` always points
at the current iteration), and probing for the `features` key already distinguishes v1 from v2.
Recorded for T-029 in `context/discoveries/T-047.md` instead. Also discarded, same round and same
place: size and cardinality bounds on `len(features)`/`len(columns)`/`len(operation)`/
`len(rationale)`/`params` list length — practically bounded by the node's `max_tokens: 4096`, and
v1 had none either, so it is low risk against the cost of a new limit in a just-pinned contract.
And discarded: adding `cat boost` to the target tuple to survive an unconditional camel split
(matching both variants is strictly better and leaves the curated tuple alone).

## 2026-08-20 — T-047 [pipeline-agent]
Decided: Second review round on the v2 fit-scope keyword floor. `standardize` and
`standardization` are **removed** from `_SCALER_KEYWORDS` (they were added in round 1 of this same
review) and added instead to the module's deliberately-excluded bare-stem list. `cat boost` is
added to `_TARGET_ENCODING_KEYWORDS` and `most frequent imputer` to
`_STATISTICAL_IMPUTATION_KEYWORDS`. `_normalized_operation_variants`' docstring is corrected: it no
longer claims the dual-variant match "cannot introduce a false positive the unsplit form did not
already have".
Why: the guard's conservatism is **not symmetric**, and round 1 reasoned as if it were. The stated
premise — "forcing `per_fold` on a stateless operation produces identical output, so over-matching
is cheap" — is false here: `_matched_fit_scope_family` does not coerce `fit_scope`, it raises
`ValueError`, and `LLMNode.__call__` (`src/nodes/llm/base.py:83-94`) has no `try/except` and no
node wrapper in `src/graph/` catches it. A false positive therefore **aborts the Phase 4 run on a
correct response**. A false negative has three layers behind it: the prompt's general "anything
fitted is `per_fold`" rule, `code_critic`'s leakage rubric, and the other keywords of the same
family — a covered silent leak. Over-matching has nothing behind it. That is why bare stems are
strictly bad rather than a balanced trade-off, and `standardize`/`standardization` are bare stems:
direct synonyms of `normalize`/`normalization`, which the module already excludes for exactly this
reason. Executed evidence: `standardize_address_format`, `standardize_text_case`,
`standardize_country_codes`, `StandardizePhoneNumber` and `standardize_units_to_metric` all
returned `scaling / normalization`. Genuine z-scoring stays covered by `standard scale(r)`,
`zscore`, `z score`, `minmax`, `maxabs`. Conversely `CatBoostEncoder` — `category_encoders`' real
class name, in the target-leakage family, the most severe one — returned `None`, because the tuple
carries `catboost` concatenated and the camel split produces `cat boost`; and
`most_frequent_imputer` returned `None` although the prompt promised "the same three forms for
`mean_`, `mode_` and `most_frequent_`", the exact prompt/validator drift T-022's decision record
exists to prevent. Fixed on the tuple side, not by weakening the prompt:
`SimpleImputer(strategy="most_frequent")` is real sklearn. All four imputation stems now have all
three forms; the prompt no longer over-claims.
Affects: `src/nodes/llm/feature_engineer.py` (family-constant block comments, three tuples,
`_normalized_operation_variants` docstring), `tests/unit/nodes/llm/test_feature_engineer.py`,
`config/prompts/feature_engineer/v2.md`, `docs/pipeline.md` § leakage-prone operation families.
Implementation note: the corrected docstring keeps the one claim that *is* provable — the variant
tuple always contains the plain separator-collapsed form, which is the pre-camelCase
normalization, so the match set is a strict superset and the dual-variant approach loses nothing.
It matches strictly more strings, which is its purpose, and can therefore surface a false positive
the unsplit form lacked (`StandardizeTextCase`, `ModeFillColorFlag`, `ImputeMeanFlagOnly`,
`FillnaMeanIndicator`, `TargetEncoderFreeBaseline` — all match split, none unsplit). Every one has
a snake_case twin that false-positives under both forms, so the root cause is keyword choice, not
splitting; the mitigation is keyword discipline, not a property of the splitting.
Discarded: keeping `standardize`/`standardization` behind a qualifier requirement
(`standardize numeric`, `standardize features`) — rejected because it relies on phrasing the LLM
has no reason to produce, so it would buy back almost none of the lost coverage while keeping a
bare stem's shape in the tuple; `standard_scale`/`z_score` already cover the real technique and the
prompt now names them. Also note this round **reverses** the previous entry's "discarded: adding
`cat boost` to the target tuple": matching both variants is still strictly better than splitting
alone, but it does not reach `CatBoostEncoder`, whose split form no concatenated keyword can match
— the two are complementary, not alternatives.
