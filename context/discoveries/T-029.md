## OPEN — 2026-08-20 [pipeline-agent (T-029) → infra-agent]
`coder` (T-029) generates training scripts that dispatch on `design.json`'s canonical
`model_family` token. Of the ~18 tokens the 5 Phase-5 specialists can emit, roughly 8 have
no installed runtime in `pyproject.toml`: `tabnet`, `node`, `transformer_finetune` (need
`pytorch-tabnet`/`torch`/`transformers`), `arima`, `exponential_smoothing`, `prophet` (need
`statsmodels`/`prophet`), and `mlp` only if the generated script prefers `torch` over
sklearn's `MLPClassifier`/`MLPRegressor` (the prompt instructs the sklearn preference, but
cannot force it).

Per this task's own scope, `coder` does not work around this: the prompt instructs it to
prefer already-installed libraries and to let an `ImportError` for a genuinely unrunnable
family surface as a normal (loud, attributable) execution failure — `coder`'s bounded
execution-retry loop will exhaust and raise `ValueError` naming the underlying
`ImportError`/`ModuleNotFoundError` from `code_executor`'s stderr. This means any real run
where a specialist selects `arima`/`prophet`/`exponential_smoothing`/`tabnet`/`node`/
`transformer_finetune` will currently fail Phase 5 outright for that experiment, with no
fallback.

Action needed: `infra-agent` should decide whether to add `statsmodels`, `prophet`, `torch`,
`pytorch-tabnet` and `transformers` to `pyproject.toml` — or whether `timeseries_specialist`/
`deep_learning_specialist`/`nlp_specialist`'s allowed `model_family` sets should be narrowed
to what's actually installed (a `src/nodes/llm/` change to those already-landed specialists,
outside `coder`'s scope).
Task where this should be addressed: unassigned (infra-agent for the dependency route, or the
relevant specialist-owning task for the narrowing route)
Status: open

## OPEN — 2026-08-31 [pipeline-agent (T-029, adversarial review round 3) → T-033's owner / report_writer.py]
`report_writer.py` (T-033, already landed — a different task's file, out of scope for this PR)
renders each `state["experiments"]` entry verbatim via `_render_experiment_entry`, including the
cached `cv_score` field. Per `coder.py`'s own documented design (see its module docstring, "How
`code_critic`'s outer retry loop composes with this one"), only the *first* graph-level `coder`
call for a given iteration ever produces a delta that LangGraph applies to real
`state["experiments"]` — every `code_critic`-triggered `iterate` re-invocation of `coder`
overwrites `exp_dir` on disk (a fresh `results.json`, possibly with a different `cv_score`) but
never updates `state["experiments"]`, since those re-invocations bypass the graph and only mutate
`code_critic`'s own local `working_state`.

`score_evaluator` is unaffected — confirmed it re-reads `results.json` fresh from disk via each
entry's `path` pointer, never trusting the cached `cv_score`. `report_writer` does not follow that
same pattern: it trusts the cached field directly. So whenever `code_critic` forces at least one
`iterate` cycle for an experiment — the repo's own smoke-test mock LLM does this by default, so
this is a common path, not a rare edge case — the human-facing final report can show a stale
`cv_score` that differs from what is actually in `results.json` on disk at that experiment's
`path`.

Action needed: have `report_writer` re-read `results.json` from each entry's `path` at render
time rather than trusting the cached `cv_score` field, mirroring the pattern `score_evaluator`
already uses.
Task where this should be addressed: unassigned (T-033's owner, or a follow-up task against
`report_writer.py`)
Status: open

`code_executor.execute()` (`src/tools/code_executor.py`, infra-agent's, not touched by this PR)
has no filesystem/network sandboxing beyond stripping credential env vars. `coder` is the first

actually executed with real subprocess/filesystem reach (every other node only writes structured
JSON). Worth flagging as a candidate for OS-level sandboxing (container or network-namespace
isolation) now that this combination — LLM-authored code, real execution, no sandbox — is
operationally reachable rather than theoretical. Advisory awareness, not a specific actionable bug
in this PR.
