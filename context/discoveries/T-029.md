## OPEN — 2026-08-20 [pipeline-agent (T-029) → infra-agent]
`coder` (T-029) generates training scripts that dispatch on `design.json`'s canonical
`model_family` token. Of the ~18 tokens the 5 Phase-5 specialists can emit, roughly 8 have
no installed runtime in `pyproject.toml`: `tabnet`, `node`, `transformer_finetune` (need
`pytorch-tabnet`/`torch`/`transformers`), `arima`, `exponential_smoothing`, `prophet` (need
`statsmodels`/`prophet`), and `mlp` only if the generated script prefers `torch` over
sklearn's `MLPClassifier`/`MLPRegressor` (the prompt instructs the sklearn preference, but
cannot force it).

Per this task's own scope, `coder` does not work around this: the prompt instructs it to
prefer already-installed libraries and to let an `ImportError` for a genuinely unrunnable
family surface as a normal (loud, attributable) execution failure — `coder`'s bounded
execution-retry loop will exhaust and raise `ValueError` naming the underlying
`ImportError`/`ModuleNotFoundError` from `code_executor`'s stderr. This means any real run
where a specialist selects `arima`/`prophet`/`exponential_smoothing`/`tabnet`/`node`/
`transformer_finetune` will currently fail Phase 5 outright for that experiment, with no
fallback.

Action needed: `infra-agent` should decide whether to add `statsmodels`, `prophet`, `torch`,
`pytorch-tabnet` and `transformers` to `pyproject.toml` — or whether `timeseries_specialist`/
`deep_learning_specialist`/`nlp_specialist`'s allowed `model_family` sets should be narrowed
to what's actually installed (a `src/nodes/llm/` change to those already-landed specialists,
outside `coder`'s scope).
Task where this should be addressed: unassigned (infra-agent for the dependency route, or the
relevant specialist-owning task for the narrowing route)
