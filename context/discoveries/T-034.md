## OPEN — 2026-09-12 [api-agent (T-034) → frontend-agent]
`src/api/` now implements run management (`POST/GET /api/runs`, `GET /api/runs/{id}`,
`POST /api/runs/{id}/resume`). Final response shapes differ from
`frontend/src/api/types.ts`'s provisional guess:

- All keys are **snake_case** matching `LabState` field names — `run_id`,
  `competition_name`, `workspace_path`, `status`, `phase`, `current_iteration`,
  `best_score`, `created_at`, `updated_at` — not camelCase (`types.ts`'s `Run` uses
  `id`/`competitionName`/`currentPhase`/`currentIteration`/`bestScore`/`createdAt`/
  `updatedAt`, and is also missing `workspace_path`).
- `POST /api/runs`'s request body is `{competition_name, workspace_path, max_iterations?}`
  — not `types.ts`'s `CreateRunPayload` shape (`competitionName`, `problemStatement`,
  `datasetPath`; no `max_iterations`).
- The resume request body key is `feedback` (not `types.ts`'s `humanFeedback`).
- `status` vocabulary matches what `types.ts` already guessed:
  `pending|running|interrupted|completed|failed`.
- `best_score` serializes as JSON `null` (never `-Infinity`) when no experiment has
  improved on the initial `float("-inf")` — matches `types.ts`'s `bestScore: number | null`
  in spirit, just under the snake_case key.
- `phase` is always present as a string (`""` before any phase has run), not
  `currentPhase: string | null`.

Please update `frontend/src/api/types.ts` and `frontend/src/api/client.ts` to match once
T-038 (frontend client) picks this up.
