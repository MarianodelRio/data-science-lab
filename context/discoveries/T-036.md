## OPEN — 2026-09-12 [api-agent (T-036) → frontend-agent]
`WS /api/runs/{id}/chat` now implements the chat + interrupt-forward channel. The real
frame shapes (documented in `docs/api.md` § WebSocket) differ from
`frontend/src/api/types.ts`'s provisional `ChatMessage` type:

- All frames are plain snake_case JSON objects with a `type` discriminator, not the shape
  `types.ts` currently guesses.
- **Client → server**: `{"type": "question", "text": "..."}`,
  `{"type": "approve", "feedback": "..."}`, `{"type": "redirect", "feedback": "..."}` —
  `feedback` may be `""` ("proceed, no comment"); `approve` and `redirect` are the exact
  same server-side operation, differing only in the `feedback` text (redirect does **not**
  re-run the phase that just completed).
- **Server → client**: `{"type": "checkpoint", "phase": ..., "summary": ...}` (sent once,
  automatically, right after connecting, only if the run is currently interrupted),
  `{"type": "answer", "text": "..."}` (reply to a `"question"`),
  `{"type": "resumed", "run_id": ..., "status": "running"}` (an approve/redirect was
  accepted — same underlying call as `POST /api/runs/{id}/resume`), and
  `{"type": "error", "detail": "..."}` (malformed frame, unknown type, or a rejected
  approve/redirect). An unknown `run_id` sends one `error` frame then closes the socket;
  every other error frame leaves the socket open.
- Conversation history is kept only in memory for the lifetime of the connection — it is
  never persisted to `LabState` or the workspace, so the frontend is the sole owner of
  chat history across reconnects.

`frontend/src/api/client.ts`) against this shape once the frontend chat task picks it up.
