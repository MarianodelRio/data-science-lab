## OPEN — 2026-09-13 [Orchestrator (T-043 adversarial review) → pipeline-agent / infra-agent]
`docker-compose.yml`'s `mlflow` service backs onto a single global directory
(`${WORKSPACE_ROOT}/mlruns`, `${WORKSPACE_ROOT}/artifacts`) shared across every competition —
this mirrors `design.md` § Docker deployment's own compose snippet verbatim, it is not a
deviation introduced by T-043. `design.md`'s ML workspace layout (line 65) and § RAG
architecture both describe experiment tracking as scoped per-competition
(`~/competitions/{competition_name}/mlruns/`), so once this compose file makes MLflow a real
always-on service (per `context/discoveries/T-037.md`), every competition's runs, params and
artifacts land in the same MLflow backend store and experiment IDs are no longer namespaced by
competition. Not a T-043 bug — reproducing `design.md`'s own example correctly — but the
resulting behavior contradicts the per-competition design intent now that it is a real running
system instead of a diagram in a doc.
Required action: either accept a single shared MLflow instance across all competitions
(distinguish runs via a competition-name tag/experiment-per-competition inside MLflow itself)
or change the compose mount/command to scope `--backend-store-uri`/`--artifacts-destination`
per competition (harder, since MLflow's `--host 0.0.0.0` server process is single-instance and
compose doesn't know the competition name at container-start time). This needs an architectural
decision, not a docker-compose tweak.
