# Data Science Lab — Design

## Architecture overview

A multi-agent system built on LangGraph that takes a problem statement + dataset and produces a
complete, reproducible ML project repository. The system runs through seven phases — Understanding,
Research, Baseline, Design, Implementation, Evaluation, Delivery — iterating autonomously until the
user is satisfied. Three mandatory human checkpoints (after phases 1, 4, and 6) keep the user in
control of key decisions.

The system consists of two distinct repositories:

- **Agent system** (`data-science-lab/`): LangGraph pipeline, FastAPI backend, React UI — the
  orchestration layer.
- **ML workspace** (`~/competitions/{competition_name}/`): the repo built *by* the agents — clean
  Python scripts, notebooks, experiment artifacts, and reports. This is the deliverable.

Deployment: four Docker containers (`api`, `frontend`, `chroma`, `mlflow`). The workspace lives on
the host and is bind-mounted into the API container.

## Shared contracts

### LabState

Lightweight coordinator. Holds file paths, scalar scores, and control fields only.
No large data structures in memory — content lives on disk.

```python
class LabState(TypedDict):
    # Input
    competition_name: str
    workspace_path: str

    # File pointers (content lives in workspace, state holds the path)
    eda_report_path: str
    problem_definition_path: str
    validation_config_path: str     # immutable after Phase 1
    baseline_results_path: str      # permanent benchmark, set once
    solution_plan_path: str
    feature_spec_path: str

    # Control
    phase: str
    current_iteration: int
    max_iterations: int
    iterations_without_improvement: int

    # Scores (floats only)
    baseline_score: float           # single permanent benchmark
    best_score: float
    last_score: float
    score_delta: float

    # Experiment index (metadata only, full results in workspace files)
    experiments: list[dict]         # [{id, path, cv_score, iteration, model}]
    best_experiment_path: str       # only updated when score > best_score

    # Human checkpoint
    checkpoint_summary: str         # markdown rendered in UI
    human_feedback: str

    # LLM context (trimmed per node: last N messages + node-specific input)
    messages: Annotated[list, add_messages]
```

### WorkspaceManager API

Single point of file I/O to the ML workspace. Nodes never call the filesystem directly.

```python
class WorkspaceManager:
    def read_json(self, relative_path: str) -> dict: ...
    def write_json(self, relative_path: str, data: dict) -> str: ...  # returns abs path
    def read_text(self, relative_path: str) -> str: ...
    def write_text(self, relative_path: str, content: str) -> str: ...
    def write_notebook(self, relative_path: str, cells: list) -> str: ...
    def experiment_dir(self, exp_id: str) -> Path: ...
    def ensure_dir(self, relative_path: str) -> Path: ...
```

### LLMFactory API

Single point of LLM instantiation. Reads `config/settings.yaml` at startup.
Changing a model = changing one line in settings.yaml.

```python
class LLMFactory:
    @staticmethod
    def get(role: str) -> BaseChatModel:
        """
        Roles: advisor | reasoning | implementation | research | fast
        Provider dispatch: anthropic → ChatAnthropic
                           deepseek  → ChatOpenAI(base_url=deepseek)
                           groq      → ChatGroq
                           gemini    → ChatGoogleGenerativeAI
                           openai    → ChatOpenAI
        """
```

### AgentConfig (loaded from config/agents/{name}.yaml)

```python
@dataclass
class AgentConfig:

    prompt_version: str      # maps to config/prompts/{name}/{version}.md
```

```python
@dataclass
class PhaseConfig:
    name: str

    sequence: list[str]      # execution order
    parallel_nodes: list[str]  # nodes that run concurrently (max 2)
    critic: CriticConfig | None

```

## Non-functional requirements

| Attribute | Requirement | Architectural implication |
|---|---|---|
| **Latency** | No constraint — individual agent responses of minutes are acceptable. Full runs may exceed 1 hour. | No timeout pressure on LLM calls. Optuna inner loop uncapped (configurable). |
| **Concurrency** | Single user, single active run at a time. | No authentication, no multi-tenancy. API is single-tenant by design. |
| **Availability** | Local tool — process restart is acceptable. | SQLite checkpointer ensures every run is resumable from last completed node. No state is lost on crash. |
| **Persistence** | Prefer files over memory across the system. | LabState holds paths, not content. All agent outputs written to workspace files. Chroma and MLflow use persistent Docker volumes. |
| **Cost** | Free or near-free. Target < $0.50 per full competition run. | Fast/research agents use free-tier Groq or cheap DeepSeek. Advisor (Opus 5) called rarely — only for high-risk decisions. |
| **Data sensitivity** | Kaggle competition data (public datasets). No PII, no payments. | No encryption requirements. LangSmith off by default — data does not leave the machine without explicit opt-in. |
| **Scalability** | N/A — local single-machine tool. | No load balancing, no horizontal scaling. |

## Configuration and modularity system

All agents, phases, prompts, and model assignments are external to the Python code.
Changing behavior = editing YAML/Markdown files. No Python changes required for most modifications.

### How to add an agent

1. Create `config/agents/{name}.yaml` with model_role, prompt_version, tools, output_file_pattern
2. Create `config/prompts/{name}/v1.md` with the system prompt
3. Add `{name}` to the relevant `config/phases/{phase}.yaml` → `nodes` and `sequence`
4. Create `src/nodes/llm/{name}.py` — minimal Python, calls LLMFactory and WorkspaceManager

### How to change a prompt

Edit `config/prompts/{agent}/v1.md` or create `v2.md` and update `prompt_version: v2` in the
agent YAML. Old versions remain in git history.

### How to remove an agent

Remove from the phase YAML. The agent YAML and prompt files can stay (they become inert).

### How to change a model

Edit `config/settings.yaml` → `models.{role}.model`. All agents using that role pick it up on
next container restart.

## LangGraph topology

### Main graph

```
START
  → phase1_understanding  (interrupt)  → human approval
  → phase2_research
  → phase3_baseline        [only when current_iteration == 0]
  → phase4_design          (interrupt)  → human approval
  → phase5_implementation
  → phase6_evaluation      (interrupt)  → human decision: continue / stop
      ↓ continue                            ↓ stop
  → phase4_design (loop)             → phase7_delivery → END
```

Supervisor is a pure Python conditional edge function — deterministic, no LLM.

### Checkpointer

SQLite, always active:
```python
checkpointer = SqliteSaver.from_conn_string(f"runs/{run_id}/checkpoint.db")
# Resume after crash: graph.invoke(None, config={"thread_id": run_id})
```

### Phase subgraphs

Each phase is a compiled LangGraph subgraph. The GraphBuilder reads `config/phases/*.yaml` and
assembles them dynamically — adding a node to a phase YAML is sufficient to wire it into the graph.

## The seven phases

### Phase 1 — Understanding (sequential + interrupt)

Nodes: `data_analyst` → `problem_framer` → `validation_strategist` → `leakage_auditor` →
`analysis_critic` → **interrupt**

- `data_analyst` (LLM + code_executor): full EDA; writes `eda_report.md` and `01_eda.ipynb`
- `problem_framer` (LLM): classifies problem type and success metric; writes `problem_definition.json`
- `validation_strategist` (LLM): selects CV strategy, generates and **freezes** `fold_config.json`
- `leakage_auditor` (LLM): inspects for future leakage, target-correlated IDs, train/test contamination; writes `leakage_audit.json`
- `analysis_critic` (LLM): reviews all Phase 1 outputs for methodological soundness; max 3 retries per output

### Phase 2 — Research (parallel, max 2 concurrent)

Nodes: `[literature_researcher ‖ web_researcher]` → `competition_analyst` → `memory_manager`

- `literature_researcher` (LLM): arxiv + Semantic Scholar; structured extraction before indexing
- `web_researcher` (LLM): Tavily API; blogs, GitHub repos, technical discussions
- `competition_analyst` (LLM): Kaggle forum + top-voted notebooks; extracts winning patterns
- `memory_manager` (LLM): deduplicates and consolidates the Chroma collection

All research findings are indexed with structured metadata extracted by an LLM before embedding:
`{source, problem_type[], methods_used[], dataset_characteristics[], key_findings, relevance_score}`

### Phase 3 — Baseline (only iteration 0)

Nodes: `baseline_designer` (LLM) → `baseline_runner` (Python + code_executor)

- `baseline_designer` reads `problem_definition.json` + `eda_report.md` and designs a non-trivial,
  non-tuned baseline appropriate to this specific problem. Not hardcoded — the LLM adapts to the
  problem structure (e.g. imbalanced tabular → LightGBM defaults + class_weight='balanced').
- `baseline_runner` implements and executes the design using frozen folds. Logs to MLflow.
- The resulting score is the **single permanent benchmark**. Never re-run. Never overwritten.

### Phase 4 — Design (sequential + interrupt)

Nodes: `solution_architect` → `feature_engineer` → `analysis_critic` → **interrupt**

- `solution_architect` (LLM): reads RAG + baseline + previous error diagnosis; designs strategy
- `feature_engineer` (LLM): designs feature transformations; fold-aware target encoding to prevent leakage
- `analysis_critic` (LLM): validates plan coherence and feasibility; max 3 retries

### Phase 5 — Implementation (sequential)

Nodes: `specialist_selector` → `specialist` → `coder` ↔ `code_executor` [Optuna loop] → `code_critic`

- `specialist_selector` (Python): reads `solution_plan.json`, decides which specialist to activate
- Active `specialist` (LLM): one at a time. Designs experiment with Optuna search space.
  Available: `classical_ml_specialist`, `deep_learning_specialist`, `nlp_specialist`,
  `timeseries_specialist`, `ensemble_specialist` (activated only when relevant)
- `coder` (LLM): writes Python files to workspace via WorkspaceManager; executes via code_executor;
  iterates on errors. Optuna runs inside the subprocess (50 trials, early stop after 20 without improvement).
- `code_critic` (LLM): reviews generated code for reproducibility, inference pipeline leakage,
  clean structure; max 3 retries

### Phase 6 — Evaluation (sequential + mandatory interrupt)

Nodes: `score_evaluator` → `feature_importance_extractor` → `error_analyst` →
`hypothesis_generator` → `experiment_designer` → **interrupt**

- `score_evaluator` (Python): compares CV score vs baseline and all previous iterations; computes deltas
- `feature_importance_extractor` (Python + SHAP): tree models only; omitted for neural
- `error_analyst` (LLM): diagnoses root cause of score
- `hypothesis_generator` (LLM): proposes prioritized hypotheses; queries RAG to avoid repeating failures
- `experiment_designer` (LLM): converts hypotheses to concrete next-iteration plan

### Phase 7 — Delivery (sequential)

Nodes: `reviewer` → `report_writer` → `kaggle_client`

- `reviewer` (LLM): code review — fixed seeds, relative paths, no debug prints
- `report_writer` (LLM): generates `final_report.md`
- `kaggle_client` (Python): formats submission, uploads, retrieves LB score; flags CV/LB divergence

| | `analysis_critic` | `code_critic` |
|---|---|---|
| Activated in | Phase 1, Phase 4 | Phase 5 |
| Reviews | EDA quality, problem framing, solution plan, feature spec | Generated Python code |
| Rubric | Methodological rigor, design-level leakage, plan realism | Reproducibility, inference pipeline leakage, executability |
| Max retries | 3 per output | 3 per artifact |

## RAG architecture

**Vector store**: ChromaDB server (Docker), one collection per competition keyed by `competition_name`.
Persists across sessions of the same competition. New competition = new collection.

**Embeddings**: `nomic-embed-text` via sentence-transformers — local, no API cost, no data leaves the machine.

**Indexing pipeline**:
1. Raw document arrives (paper, web page, forum post, experiment result)
2. LLM extracts structured metadata: `{source, problem_type[], methods_used[], dataset_characteristics[], key_findings, relevance_score}`
3. Text embedded locally
4. Chunk + metadata stored in Chroma

**Retrieval**: dense similarity + metadata filter
```python
collection.query(
    query_texts=["class imbalance LightGBM"],
    where={"problem_type": {"$in": ["binary_classification"]}},
    n_results=10
)
```

**What gets indexed**: papers, web findings, Kaggle forum, experiment results with full context,
error diagnoses, validated/invalidated hypotheses.

## UI architecture

### Backend — FastAPI (`src/api/`)

| Endpoint | Protocol | Purpose |
|---|---|---|
| `GET /api/runs` | REST | List all runs |
| `POST /api/runs` | REST | Create and start a new run |
| `GET /api/runs/{id}/events` | SSE | Stream pipeline events in real time |
| `WS /api/runs/{id}/chat` | WebSocket | Bidirectional chat with explainer agent |
| `POST /api/runs/{id}/resume` | REST | Submit human_feedback, resume from interrupt |
| `POST /api/runs/{id}/submit` | REST | Trigger Kaggle submission |
| `POST /api/mlflow/open` | REST | Launch `mlflow ui` subprocess, return URL |

The LangGraph pipeline runs as an asyncio background task inside the API process.
Events are emitted to an `asyncio.Queue` and streamed via SSE to the frontend.

### Explainer agent

Separate LangGraph subgraph invoked via WebSocket. Read-only access to LabState, workspace files,
and Chroma. Activated automatically at interrupt points; also available on-demand for questions.
Also serves as the interface for human interrupt decisions (approve / redirect via chat).

### Frontend — React + Vite (`frontend/`)

| Component | Purpose |
|---|---|
| `PipelineView` | Current phase, active node, timeline with durations — live via SSE |
| `ExperimentsTable` | CV scores per iteration, delta vs baseline, best model highlighted |
| `Chat` | WebSocket connection to explainer agent; auto-activates at interrupts |
| `FileViewer` | Markdown renderer for eda_report.md, final_report.md, feature_importance |
| `ActionBar` | Kaggle submission button + open MLflow button |

## Observability

### Layer 1 — Local structured logs (always on)

Path: `runs/{run_id}/execution.jsonl`

A LangGraph callback fires on every node entry and exit:
```json
{"timestamp": "...", "run_id": "...", "iteration": 1, "phase": "phase4_design",
 "node": "solution_architect", "event": "end", "duration_ms": 4820,
 "tokens_in": 3200, "tokens_out": 890, "model": "deepseek-v4-flash",
 "output_summary": "Designed LightGBM + stacking strategy for iteration 2"}
```

### Layer 2 — MLflow experiment tracking (embedded)

File-based backend: `workspace/{competition}/mlruns/`
Each training run logs: params, CV scores, OOF predictions path, model artifact path.
Optuna trials logged via `mlflow-optuna` integration.
UI: `POST /api/mlflow/open` launches `mlflow ui` subprocess → opens in new browser tab.

### Layer 3 — LangSmith (opt-in)

Off by default. Activated via `LANGCHAIN_TRACING_V2=true` in `.env`.
Full agent traces with inputs/outputs and latency. No data leaves the machine without this flag.

## Critical invariants

1. **`fold_config.json` is immutable** after Phase 1 — no agent may modify it at any iteration
2. **`WorkspaceManager` is the sole file I/O point** — nodes never call the filesystem directly
3. **`best_experiment_path` updates only when `score > best_score`** — no regression on best result
4. **Phase 3 runs only when `current_iteration == 0`** — baseline is a permanent benchmark
5. **`analysis_critic` and `code_critic` enforce max 3 retries** — no infinite loops
6. **Max 2 LLM agents run concurrently** — only in Phase 2 (Research)
7. **`specialist_selector` activates one specialist per iteration** — sequential implementation
8. **Config files are the only place to change agent behavior** — no hardcoded prompts in Python

### Test structure

```
tests/
├── unit/
│   ├── nodes/           ← one file per node, LLM mocked via fixture
│   ├── tools/           ← code_executor, rag, workspace_manager
│   └── llm/             ← factory, providers
├── integration/
│   ├── phases/          ← phase subgraphs with Chroma test instance + mock LLM
│   └── api/             ← FastAPI TestClient
├── smoke/
│   └── test_full_run.py ← iris or titanic sample, Groq free tier
└── fixtures/
    ├── datasets/        ← tiny CSVs (iris, titanic head)
    ├── responses/       ← mocked LLM responses as JSON (deterministic tests)
    └── workspaces/      ← pre-built workspace states for mid-pipeline testing
```

No network calls in unit tests. Integration tests use a real Chroma instance
(separate Docker container in CI). Smoke tests call real LLM APIs (Groq free tier).
